## 3. 关键证据判断

本次事件能推进到“确认安全事件”的交付门槛，核心是 6 条确认事件形成了自我增强的证据链，而不是单点信号重复。最上游的 DNS 事件证实 `ws-eng-02` 在 TLS 信标建立前主动解析了稀有域名 `sync-cdn-notify.net`，排除了随机流量触碰 C2 的可能。随后的 TLS 会话被 JA4 指纹 `t13d1516h2_2ba4190accc0_13fe129f5abc` 精确命中，且该指纹本身被标记为多主机信标扩散家族，这赋予了整条链一个稳定的技术特征——即使本地情报库未命中该 IOC，指纹匹配本身已经构成触发级证据。

更进一步，`ws-eng-02` 在告警后 4 分钟对同一 C2 的重复连接，将偶发性可疑会话转化为持续性信标行为。紧随其后的 rundll32 加载器执行虽然只停留在可疑线索阶段，但它与信标重连的时间贴合关系强烈指向 C2 下发载荷后的本地执行动作。进入横向阶段，PsExec 远程服务创建事件出现在 rundll32 之后仅 3 分钟，且目标主机 `ws-eng-05` 在此后 7 分钟主动连接了与种子完全相同的 C2 基础设施 `sync-cdn-notify.net / 203.0.113.77`。这个闭环——从种子主机到目标主机的横向操作，再到目标主机独立命中同一 C2——是确认 `ws-eng-05` 纳入受影响范围的核心证据，也阻止我们把该事件退化为单主机误报。

但上述证据有明确上限。rundll32 执行事实仅指出 `rundll32.exe` 以可疑方式从用户可写路径启动了一个加载器 DLL，缺乏完整命令行参数、加载的 DLL 名称与哈希值、父进程链和落地文件。正因为这些缺口，我们只将其判断为“可疑执行线索”而不是“已确认的恶意加载器成功执行”。PsExec 远程服务创建事件我们也只表述为“横向推进线索”，因为在当前目录中，没有 `ws-eng-05` 上对应的主机执行细节、载荷落地或独立取证闭合，所以不能表述为“已确认存在横向推进线索到 ws-eng-05 且恶意载荷已在目标端执行”。

## 4. 影响范围、候选对象与外部基础设施

已确认受影响资产目前限定在 `ws-eng-02` 和 `ws-eng-05` 两台工程工作站。`ws-eng-02` 作为种子资产贯穿了整个攻击链的前半段：DNS 解析、TLS 信标建立、重复外联、主机可疑执行和 PsExec 横向发起，五项确认事件全部落地在这台机器上。`ws-eng-05` 虽然处在维护窗口期间且存在合规补丁活动，但 PsExec 远程服务创建后不到 10 分钟它就主动向核心 C2 发起连接，这使它的确认程度达到“已纳入确认受影响范围”，而非仅凭远程操作的单向痕迹。需要强调，“确认受影响范围”不等于“受影响主机”；这意味着这两台工作站必须被隔离和取证，但现有证据尚未达到足以证明攻击者已在这两台主机上完整执行恶意代码并建立持久化的程度。

候选扩线对象以 `ws-eng-09` 以及 WMI 远程进程创建事件所触及的 `10.70.3.90` 为核心。`ws-eng-09` 解析了 `cdn-notify-edge.net` 并在候选事件中连接了次级基础设施 `198.51.100.44`，关联性不容忽视。但 WMI 事件缺乏独立验证指示物，次级域名 `cdn-notify-edge.net` 的本地情报命中仍为空白，因此 `ws-eng-09` 只是待确认关联资产，不可在报告正文中将之表述为已确认受影响。同一类候选线索还包括 `ws-lab-02`，但它仅在共享托管 IP `198.51.100.44` 的背景下出现，与事件的连接更弱，只能作为背景对象的扩展查询候选。

外部基础设施被严格划分为两层。核心外部基础设施是 `sync-cdn-notify.net` 和与之对应的 IP `203.0.113.77`。这两个对象在种子告警、后续信标重连以及第二台主机的外联中反复出现，是事件中最稳定的 C2 锚点，应立即作为封禁和出口回溯的核心对象。次级外部基础设施涉及 `cdn-notify-edge.net` 和 `198.51.100.44`，由于 `198.51.100.44` 被证实承载了与事件无关的 QA 遥测流量 `telemetry-collector.example`，该 IP 存在明显的共享托管属性，因此只能作为外联判断对象和关联基础设施，不能直接定性为恶意 IP。二级域名 `cdn-notify-edge.net` 同样停留在已验证待确认状态，其潜在的 C2 角色需要在命中了独立情报后才能升级。

## 5. 反证、替代解释与未闭合缺口

当前事实中最为关键的替代解释集中在 `ws-eng-05`。该主机在同一小时内存在已批准的 SCCM 补丁阶段活动，并且主动访问了微软授权的 Windows Update 端点 `download.windowsupdate.com / 13.107.246.45`。这一背景意味着 `ws-eng-05` 上部分进程创建和管理活动可能与合法的系统更新流程重叠，尤其在 PsExec 远程服务创建发生的前后时间段，无法排除部分事件由管理员或补丁流程触发的可能性。这直接限制了我们不能仅凭“PsExec 后出现 C2 外联”就将全部活动闭环归因于攻击者横向移动完成，而是需要主机侧执行日志进一步拆解。

反证压力的另一个来源是次级 IP `198.51.100.44` 上的共享托管证据。`ws-lab-02` 发起的 `telemetry-collector.example` 对外连接命中了相同的 IP，且这一行为发生在完全不同功能区域（实验室环境的 QA 遥测）。这意味着即便多个工作站接触了 `198.51.100.44`，也不能直接推导出它们都与恶意 C2 通信，该 IP 在基础设施判定中的分量因此显著下降。

当前报告框架识别并明确呈现了多个未闭合缺口。首要缺口是扩线得到的候选事件尚未完成独立验证，未能确定应把哪几条候选线索从边界提入主证据链。第二个缺口是围绕当前 关键关联指标 的更大范围复现搜索仍然缺失——我们不知道同时间窗内是否存在更多工作站访问了 `sync-cdn-notify.net` 或 `cdn-notify-edge.net`。第三个关键缺口在于主机侧执行验证未能完全闭合：rundll32 的完整命令行和落地 DLL 仍未获取，`ws-eng-05` 和 `ws-eng-09` 上是否出现相同的加载器行为或内存注入证据也未确认。最后，维护窗口和补丁背景的核查仍是开放状态，未能明确区分管理活动与恶意行为的边界。这些缺口不会推翻当前确认结论，但集中划定了判断上限——事件范围和归因强度不应超出上述缺口能够支持的边界。
