## 3. 关键证据判断

本次研判并非依靠孤立告警，而是依靠行为序列上的证据链条完成定性。种子告警的 JA4 指纹 `t13d190900_44ac2200b3c1_ab11cd22ee44` 是整个事件最直接的识别特征，它专门关联到 `Suspected cloud-storage exfil chain` 这种针对 T1567.002（向云存储外传数据）场景检测的 TLS 交互模式。此告警一旦触发，意味着不仅进行了 TLS 连接，而且其双方协商的加密套件、握手模式与已知云存储外传工具集或家族特征相符，它直接排除了单纯的误触发的常规云流量可能性。

告警触发前后的一系列顺序事件构成了严密的逻辑链。`ws-rnd-04` 解析 `files-sync-share.net` 发生后不久，主机层捕获的 `sync.ps1` 执行（证据 evt-604）至关重要。该脚本位于用户的 `AppData\Roaming` 路径内，通常对应后台任务或远程下发脚本的存放地，它不是系统进程或正常办公软件所调用的组件。紧接着，`7z.exe` 明确创建了项目名命名的压缩包，并将其最终重写为 `C:\Users\Public\Music\cache.dat` （证据 evt-606）。这一连串流程将外传对象（研发原型）与外传动作（伪装、压缩、加密上传）固定在了一起。尽管 evt-614 明确指出 EDR 未完整保留该 PowerShell 的实际命令行参数，这会限制我们对脚本具体参数的复现能力并形成了一条主机侧的取证缺口，但它并不削弱“脚本被调用、数据被打包、数据已外释”这前后因果的主体判断。最后，DLP（evt-608）捕捉到无法解密的巨大上行密文流，且对外连接域名未经本地情报库核定为已知允许的商用云服务（背景 cl-02），从而彻底夯实了“非法外传”的定性。

## 4. 影响范围、候选对象与外部基础设施

目前已确认的受影响范围为内部研发工作站 `ws-rnd-04` (源 IP: 10.90.2.44)。该资产作为种子资产，承担了从解析域名到执行脚本、打包数据及完成加密上传的全套攻击链，被判定为本次外传的执行点。需要强调，“确认受影响”指的是确认该资产上发生了高安全风险的异常外传事件，应将 `ws-rnd-04` 立即纳入严格的隔离取证范围。调查过程中捕获的另一核心资产 `ws-rnd-09` (10.90.2.49) 在 UTC 17:05 也曾访问同一套外部基础设施。由于此次尝试仅此一次，且该主机在 UTC 17:08 存在经批准的维护窗口备份作业记录，目前必须将 `ws-rnd-09` 维持为待确认的候选关联对象。不能将其直接提升为已控制或已被外传的主机，但其那一次对罕见恶意域名的访问具有极高的调查优先权。另一台实验室工作站 `ws-rnd-12` (10.90.8.12) 虽然也联系了 IP 198.51.100.144，但经由的域名是 `filesync-cdn.example`，表明该 IP 落在共享云分发基础设施上，也解释了该 IP 不具备唯一恶意属性，这是一个帮忙收窄主机确认范围的关键反例。

外部关联基础设施方面，核心外联对象 `files-sync-share.net` 及其对应的反向解析 IP `198.51.100.144` 构成了本次外传的主要接收侧。该 IP 在整个分析窗口内反复出现，是主证据链中不能绕开的关键落脚点。伴随主文件传输后解析的姊妹域名 `api.files-sync-share.net` 则极可能承担回联或 API 接口控制任务。这三处外部设施构成了攻击者或代理的服务端基础设施，不是内部受控资产，需重点排查、封禁并利用 DNS 日志回溯所有内网主机对这些出口的访问记录。

## 5. 反证、替代解释与未闭合缺口

在限定以上结论时，调查过程中也识别出了明确的边界和限制性事实。首先，围绕 `ws-rnd-09` 的额外通信，除了备选事实外，它在通信发生的同一小时内存在正常执行的审批备份任务。这个背景解释强有力地限制了把 `ws-rnd-09` 直接归入被外传资产范围的冲动，目前只能将其标记为候选。对于事件核心的 `ws-rnd-04`，调查发现在可疑外传的相同监控区间内，该主机也存在向 `company-my.sharepoint.com` （解析至 13.107.136.9）发出的合法公司 SharePoint 同步流量记录。这属于正常的业务基线，与 `files-sync-share.net` 的诡异通信意图形成鲜明对比，但它同时提醒我们，分析时需要排除用户混淆存储界面的可能性，尽管从域名注册罕见度、任务操纵脚本和隐藏路径来看，“正常同步误操作”在逻辑上很难成立，属于极低概率情景。

其次，主机侧的证据缺口目前仍是关键的未闭合限制点。事件 evt-614 证实 EDR 缺失了 PowerShell 的完整执行参数，这直接阻碍了对 `sync.ps1` 执行意图的完整重建，无法确认脚本内嵌的硬编码凭证或 API 密钥。这使我们在判断“是否已存在完整的持久化机制”或“是否有横向移动准备”方面受限，目前不能给出更激进的结论。当前依然存在两条急需解决的显式缺口：一是尚未完成围绕 `files-sync-share.net` 及其解析 IP 的全网显性扩线检索，无法断言是否还有其他沉默资产在较早或稍晚时间窗口内向这些基础设施暴露过数据；二是缺少对内部共享基底、补丁计划或周期性系统维护窗口的专门排查，无法彻底排除其他 `Service Accounts` 或系统脚本无意命中这些虚拟托管 IP 的概率。
