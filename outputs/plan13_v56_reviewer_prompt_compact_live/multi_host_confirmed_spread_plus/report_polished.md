## 1. 事件结论与当前判断

## 3. 关键证据判断

当前确认主链之所以能够支撑事件成立，核心在于三个证据之间的时序咬合与因果关系。第一个锚点是种子资产的域名解析与信标连接对，ws-eng-02 先解析 sync-cdn-notify.net 然后在数分钟内产生 JA4 匹配的 TLS 信标，并且信标在告警后仍持续复用，这构成了典型的 C2 通信模式。第二个锚点是信标后紧随的主机执行线索，rundll32.exe 从用户可写路径加载 DLL，说明网络侧行为不是孤立的，而是可能伴随后续载荷操作。第三个锚点是将 ws-eng-02 与 ws-eng-05 绑定的横向移动和随后的复用通信，ws-eng-02 通过 PsExec 向 ws-eng-05 写入远程服务，ws-eng-05 随即主动连接最初的信标基础设施，这一时空上的紧密耦合使得偶然业务触碰的解释难以成立。

然而，上述主链虽然强有力，却仍不足以支撑更强力的结论。当前证据在多个维度存在断层。首先，ds-eng-02 上的可疑执行事件虽然提供了一条执行链线索，但缺乏命令行、落地文件细粒度和父子进程关系，无法确认该执行是否确实完成了载荷加载、进程注入或内存展开。其次，ds-eng-05 上未获取到与此横向移动对应的主机执行日志，无法判断远程服务创建后是否在目标侧启动了恶意代码、是否已驻留或持久化。再次，候选事件 evt-809、evt-810 和 evt-811 尚未通过本地指纹、IOC 或外部威胁情报独立验证，它们不能作为结论性的证据链延长。这些缺口将结论的上限稳定在“已确认多主机受波及且存在横向移动迹象”，而不囊括“已观察到完全控制第二目标”“横向闭环已经形成”或“数据已外传”等过度断言。

## 5. 反证、替代解释与未闭合缺口

在本案中，存在一些可能引入边界模糊的背景信号和替代解释，但它们不足以推翻主链结论。ws-eng-05 在横向移动事件发生前后，存在一条与 SCCM 补丁维护窗口相关的主机上下文事件和一条指向 download.windowsupdate.com 及 13.107.246.45 的 Windows Update 下载流量。这些行为在时间上与信标通信交叉，必须严肃对待，因为它们可能代表部分边界流量被误读。然而，维护或补丁流量无法解释 ws-eng-05 为何在紧接横向移动之后，主动连接一个此前已由 ws-eng-02 标记为恶意的 C2 信标基础设施，因为 sync-cdn-notify.net 和 203.0.113.77 与微软官方补丁服务或 SCCM 部署链路在域名基线和 IP 归属上均无已知交集。这些背景信号因此仅用于收窄结论边界，即 ws-eng-05 上的某些单条流记录如果脱离主链单独审视，其置信度可能降低，但整体链条的方向维持不变。
